# Как идёт ревью после `/pr all`

Что происходит по порядку: что открывается, зачем и что приходит в чат. Описано поведение версии 3.14.1.

## 1. Вкладка, где набрали `/pr all`

### 1.1. Список PR

Команду перехватывает мод (`mod/register.ts`), модель не участвует. Мод запрашивает у Forgejo открытые PR (до 50, по 4
параллельно), для каждого — ревью и треды, и определяет сценарий (`scenarioOf` в `mod/status.ts`):

| Сценарий | Когда | Статус в списке |
|---|---|---|
| `review` | чужой PR, моего ревью нет | на проверке |
| `recheck` | чужой PR, после моего ревью появились коммиты или автор ответил в треде | перепроверка |
| `feedback` | свой PR, в нём есть замечания | есть замечания |
| `conflict` | свой PR в конфликте с базой | конфликт |
| остальное | — | ждём автора, ждём ревью, готов к слиянию |

Дальше идут только первые четыре — «есть дело». PR с моим действующим апрувом в список не попадает.

### 1.2. Где вести каждый PR

`placeAll`: при наличии Orca каждый PR получает свою вкладку, кроме своего PR, чья ветка совпадает с `main`, — он
остаётся в текущей вкладке. Без Orca вкладок нет, PR ведутся здесь по одному.

### 1.3. Вкладка для PR

`openTabs` → `createReviewWorktree`, для каждого PR:

1. Закрытый PR пропускается.
2. Голова PR подтягивается с origin: ветка, а если её нет — `refs/pull/N/head`.
3. По merge-base с `origin/<base>` проверяется, меняет ли PR файлы Claude Code:
   - **настройки, хуки, MCP** (`.claude/settings*.json`, `.claude/hooks/`, `.mcp.json` и т. п.) — вкладка **не
     открывается**: новая сессия в таком дереве выполнила бы хуки из PR на вашей машине. В ответе будет «здесь: `/pr N` —
     мод спросит перед переключением»;
   - **только инструкции агенту** (`CLAUDE.md`, `AGENTS.md`, `.claude/rules/`) — вкладка открывается **без режима auto**,
     каждая команда спросит разрешение.
4. Создаётся worktree `.claude/worktrees/pr-<N>-<ветка>` на коммите PR (detached HEAD), инициализируются сабмодули.
   Существующий worktree переиспользуется, если в нём нет изменений и идущего прогона.
5. Orca открывает терминал-вкладку `review #N` с командой
   `cd <worktree> && claude --permission-mode auto '/pr N'`.

`.claude/worktrees/` и `.review-kit/` один раз дописываются в `.git/info/exclude`: worktree не попадают в `git status`,
а файлы прогона и гайда не делают worktree «грязным» — иначе его не удалить автоматически.

### 1.4. Ответ в исходной вкладке

```
PR 140: вкладка открыта (новый worktree …/pr-140-feature-x)
PR 141: вкладка открыта (прежний worktree …)
PR 142 меняет настройки Claude Code (…) — вкладку не открываю …
PR 99: запускаю здесь
```

PR, который ведётся здесь, мод запускает сам, отправив `/pr 99`, если в этой сессии нет идущего прогона. Остальные такие
PR перечисляются строкой «Потом здесь: `/pr 100`».

## 2. Вкладка PR: `/pr N`

Новая сессия Claude стартует в worktree с `/pr N`. Обрабатывает мод: `routePr` → `startReview` → `startRun`.

1. Сценарий определяется заново — от него зависит, какой скилл продолжит.
2. Проверка прогонов: в этой сессии уже идёт другой → вопрос «Вернуться / Прервать»; прогон этого PR открыт в другой
   сессии → «Продолжить здесь / Очистить / Отмена».
3. **Диалог «Модель для ревью PR N?»** — opus / sonnet / haiku. Первое, что нужно ответить в каждой вкладке; модель
   получат агенты.
4. Переключение дерева (`planSwitch` + `applySwitch`). В worktree дерево уже на коммите PR. Здесь же считается база
   ревью; если базовая ветка удалена, база берётся от `main` с пометкой. Изменения в дереве — предложение stash.
5. Рабочая папка `.review-kit/run/N/`:
   - `context.json` — номер, заголовок, автор, свой или чужой, base/head, модель, сценарий, есть ли Plannotator;
   - `recheck.json` (перепроверка) — база дельты от моего прошлого ревью и мои прошлые замечания;
   - `intake.json` (свой PR) — замечания ревьюеров.
6. Прогон помечается активным (`session.json` и состояние мода). С этого момента guard (`mod/policy.ts`) запрещает сырые
   `git commit`, `git push`, `--force`, `rebase`, `curl -X POST` — внешние действия только через инструменты мода.
7. Мод отвечает строкой «PR 140 (bob): дерево на коммите PR, модель opus. Прогон открыт до конца ревью…» и сам отправляет
   модели промпт «Use the review-kit:pr-review-run skill for PR 140…» (для перепроверки — `pr-recheck-run`, для
   замечаний — `pr-feedback-run`, для конфликта — `confl`).

## 3. Ревью чужого PR: скилл `pr-review-run`

### 3.1. Вход агентам — `review_prepare`

Мод собирает `.review-kit/run/N/funnel/input.md`: правила проекта (из **базы**, не из PR — PR не подменит правила), дифф
и полные тексты изменённых файлов. Файл больше 60 000 символов не прикладывается; весь вход больше 500 000 — ревью
отказывается: «разделите PR». Рядом — копии правил и манифесты, какие файлы каждый агент обязан прочитать.

### 3.2. Агенты в фоне — workflow `funnel/review-funnel.js`

| Фаза | Агенты | Что делают |
|---|---|---|
| Поиск | A `correctness`, B `quality` — параллельно | A ищет ошибки, B — нарушения правил проекта. B не запускается, если правил нет |
| Опровержение | C `refuter` | получает находки A/B, сгруппированные по близким строкам, и по каждой даёт вердикт: опровергнута / подтверждена / не удалось проверить. Не ответил — вторая попытка. Находок нет — C не запускается |

Gate мода (`mod/gate.ts`) не принимает ответ агента, пока тот не прочитал целиком все файлы манифеста, — возвращает до
трёх раз.

### 3.3. Гайд, пока работают агенты

Сразу после старта workflow: «Агенты проверяют PR N — пока гайд по изменениям:» и скилл `guide` — заголовок и ссылка,
описание PR, коммиты, «Что сделано», «Узкие места», размер. Ход заканчивается фразой «Отчёт придёт, когда агенты
закончат.»

### 3.4. Сбор находок — `review_collect`

По уведомлению о завершении workflow мод разбирает ответ:

1. Опровергнутые — в «не подтверждено».
2. Проверка, что файл и строка реальны и входят в PR, а находка B цитирует настоящее правило.
3. Пороги из `config/funnel.json`:

   | Вердикт C | Уровень | Уверенность | Куда |
   |---|---|---|---|
   | подтверждена | critical, important | ≥ 75% | в отчёт |
   | подтверждена | minor | ≥ 85% | в отчёт |
   | подтверждена | critical | ≥ 50% | в отчёт, «средняя вероятность» |
   | подтверждена | important, minor | ≥ 50% | ниже порога |
   | не удалось проверить | critical | любая | в отчёт, «не проверено» |
   | не удалось проверить | important, minor | ≥ 50% | ниже порога, «C не проверил» |

4. Дубли сворачиваются. Итог — `findings.json`.

### 3.5. Отчёт в чате

1. `Вердикт:` — Blocked (есть critical), Changes requested (есть important), Approved with comments (только minor),
   Approved (ничего).
2. `Статус:`.
3. «Подтверждённые», «Подтверждено, ниже порога», «Не подтверждено», «Не проверялось».

Свой или закрытый PR — на отчёте всё заканчивается.

### 3.6. Публикация

Чужой открытый PR — диалог «Как публикуем ревью PR N?»:

- **Сразу, без Plannotator** — список всех находок, вопрос «какие публикуем», затем `review_publish` показывает итог и
  спрашивает «Да/Нет». Выбраны critical или important — запрос изменений, иначе апрув. Апрув без выбранных находок
  уходит без текста.
- **Открыть в Plannotator** — находки аннотациями поверх диффа. «Отправить аннотации» — запрос изменений, «Approve» —
  апрув; публикуется без дополнительного вопроса. Если гайд нашёл узкие места (во время ревью он сохраняет их в
  `.review-kit/run/N/hotspots.json`), вариантов два: «только находки» и «находки и узкие места гайда». Узкие места
  приходят аннотациями с первой строкой `[gN · узкое место гайда]` — это подсказки для чтения, они не публикуются, пока
  эта строка на месте; стерев её, узкое место можно отправить своим комментарием. Пока Plannotator открыт, их можно
  добавить и по просьбе («добавь узкие места») — мод дошлёт их в открытую сессию. Если после «Отправить аннотации»
  остались только узкие места, ревью не публикуется.
- **Не публиковать.**

### 3.7. Завершение — `review_finish`

Прогон закрывается, `.review-kit/run/N/` удаляется. Если веток после ревью накопилось 5 и больше, мод предлагает уборку.

Ревью или перепроверка шли во вкладке `/pr all` (в своём worktree) — мод сразу удаляет этот worktree командой из
основного дерева. Последняя строка в чате: «worktree … удалён — ревью закончено, вкладку можно закрыть». Отчёт и ссылка
остаются на экране, но команды в этой вкладке больше не работают: её дерева нет. Если в worktree есть изменения или
прогон ещё помечен активным, worktree остаётся — «worktree … оставлен — уберёт /pr cleanup». Worktree своих PR
(`feedback`, `fix`, `conflict`) автоматически не удаляются: в них могут быть неотправленные правки.

## 4. Другие сценарии во вкладках

- **`recheck`** — два workflow сразу: `statuses` (агент D: закрыты ли мои прошлые замечания) и `delta` (A/B → C только
  по новым изменениям, только important и выше). Пока работают — гайд по изменениям после моего ревью. Отчёт: режим
  (дельта или всё), прошлые замечания — закрыто / не закрыто / частично, новые находки.
- **`feedback`** (свой PR с замечаниями) — агент D классифицирует замечания ревьюеров. Пока он работает, в чате вся
  картина по PR: пронумерованные замечания к разбору со всей перепиской (пометки «код с тех пор менялся», «ревьюер не
  согласен с ответом»), затем закрытые треды и треды, где ждём ответа ревьюера. После разбора — итог под теми же
  номерами: «согласны — исправим», «уже исправлено», «не согласны — отклоняем», «вопрос — нужен ответ» или «вне задачи»
  и причина. Дальше ответы в треды (`replies_publish`) или раунд правок `pr-fix-run` с commit и push через `commit_push`.
- **`conflict`** — мод вливает базу, конфликты разрешает скилл `confl`, затем `commit_push`.

## 5. После всего

Worktree чужих ревью удаляются сами (раздел 3.7). Остаются worktree своих PR, оставленные worktree, ветки и stash —
их убирает `/pr cleanup` или «убери вкладку N»: worktree удаляются вместе с ненужными ветками, вкладки Orca закрываются.

## Что видно в каждой вкладке

1. Диалог выбора модели.
2. Строка мода «дерево на коммите PR, модель …».
3. Гайд по PR.
4. Через несколько минут — отчёт с вердиктом.
5. Диалог «Как публикуем?».
6. Ссылка на опубликованное ревью или отказ.
7. «worktree … удалён — вкладку можно закрыть».
