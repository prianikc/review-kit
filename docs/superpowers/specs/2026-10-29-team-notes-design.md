# Заметки команды: блокирующие замечания, без запретов, уборка, пагинация, CI — дизайн

## Зачем

Команда жалуется, что один PR правят «по 1000 раз»: кит запрашивает изменения почти по любой находке. Хотят, чтобы
слияние блокировали только серьёзные вещи, а остальное уходило в TODO и чинилось отдельным PR. Попутно — убрать из кита
запреты команд (это дело правил проекта и окружения), закрыть утечки рабочих файлов, неполное чтение PR и отсутствие CI.

Источник: `notes/notes.md`, пункты 1–8. Пункт 5 (разнести `register.ts` и покрыть тестами) — отдельной спекой в самом
конце работы над заметками.

## 1. Что блокирует слияние (пункты 2 и 8)

**Блокирует** — только пять категорий:
- `regression` — сломалось то, что уже работало;
- `goal` — не достигнута цель задачи (по описанию PR / тикету);
- `architecture` — архитектурная ошибка;
- `security` — ошибка безопасности;
- `rule` — нарушено правило проекта (`.claude/rules/`, `CLAUDE.md` и т.п.).

**Не блокирует** — всё остальное: баги в новом коде, не ломающие рабочее и не мешающие цели, стиль, именование,
улучшения.

Решения пользователя:
- Обе стороны: ревью кита помечает неблокирующее и одобряет; разбор замечаний к своему PR в ките превращает
  неблокирующее в TODO и роадмап.
- Роадмап — файл в репозитории проекта.

Как это выглядит:
- **Агенты A/B** вместо `critical / important / minor` ставят `blocking` с категорией из пяти или `non-blocking`.
  Находка `blocking` без категории — невалидна (как находка без сценария отказа). Рефьютер (C) проверяет и категорию:
  «сломалось рабочее» требует показать, что это работало до PR.
- **Вердикт:** выбрана хоть одна `blocking` → запросить изменения; только `non-blocking` → одобрить с комментариями;
  ничего → одобрить. Открытые треды и незакрытые прошлые замечания поднимают вердикт, только если они сами блокирующие
  (прошлое замечание было `blocking`).
- **Кто что делает.** Ревьюер файлов не пишет и в чужую ветку не пушит: его кит только публикует комментарии в ревью.
  Неблокирующий комментарий уже содержит готовый текст TODO. Файлы — TODO в коде и роадмап — пишет и пушит **автор PR**
  своим китом в работе над ошибками своего PR. Так нет конфликтов и пушей в чужую ветку.
- **Комментарий в PR:** блокирующий — как сейчас, коротко; неблокирующий — `TODO: <текст TODO одной
  фразой>`; этот текст автор переносит в код как есть.
- **Отчёт пользователю:** группы «Блокирует» (с категорией) и «Не блокирует»; пользователь по-прежнему выбирает, что
  публиковать.
- **Свой PR (`pr-feedback-run` / `pr-fix-run`):** триаж различает блокирующие и неблокирующие замечания ревьюера
  (по префиксу «TODO:» или по смыслу для ревьюеров без кита). Блокирующие — чиним в раунде.
  Неблокирующие — в том же раунде кит автора ставит в коде TODO с текстом из комментария и дописывает роадмап, коммит и
  push обычным `commit_push` в ветку своего PR, ответ ревьюеру «Перенесено в TODO: <файл>».
  Пользователь может перевести пункт в «чиним сейчас».
- **TODO в коде** (моё решение): комментарий синтаксиса файла над местом —
  `TODO(review #<N>): <суть одной фразой> — docs/roadmap/pr-<N>-review-fixes.md`.
- **Роадмап** (моё решение): `docs/roadmap/pr-<N>-review-fixes.md`, папка меняется ключом `roadmapDir` в
  `.claude/review-kit.local.json`. Заголовок «PR <N> — ревью-фиксы», пункт — чекбокс `- [ ] <файл>:<строка> — <суть> (замечание: <ссылка>)`.
  Повторный раунд дописывает, не дублирует.

## 2. Без запретов (пункт 1)

Решение пользователя: полностью отказаться от запретов в ките.
- Удаляется `mod/policy.ts` (guard сырых `git commit` / `git push` / разрушающих git-команд / записи через curl) и его
  хук `tool.call{Bash|Monitor}`, настройка `manualCommitCommands`, состояния `commitPending` / `commitTurn`.
- Из `CLAUDE.md` уходят правила про guard и `manualCommitCommands`. Инструменты `review_publish`, `replies_publish`,
  `commit_push` остаются и по-прежнему спрашивают подтверждение сами; скиллы продолжают звать их, а не сырые команды —
  это инструкция, не запрет.
- **Моё решение:** `mod/gate.ts` (агенты не сдают ответ, пока не прочли файлы манифеста) — не запрет окружения, а
  контроль качества агентов; остаётся.

## 3–4. Уборка (пункты 3 и 4) — пересмотрено

Решение пользователя: общая уборка веток и stash уходит в dev-kit (`/cleanup`), `/pr cleanup` удаляется. Ревью-кит убирает только
за собой: при завершении и тихо при следующем `/pr`. Чтение всех
страниц закрытых PR больше не нужно — его потребителем была только уборка веток.

## 5. CI (пункт 6)

GitHub Actions на PR в `main` и пуш в `main`:
- `node --test 'mod/**/*.test.ts'` на Node 24;
- проверка, что `version` в `.claude-plugin/plugin.json` больше, чем в `main`, если менялись файлы плагина;
- **моё решение:** `claude plugin validate .` — если CLI ставится в CI без входа; иначе шаг пропускается с пометкой.

## 6. Ответ в треде Forgejo (пункт 7)

Проверено: в API вашего Forgejo 15.0.3 есть `POST /pulls/{n}/reviews/{id}/comments`, кит отвечает им; UI группирует
беседу по файлу и строке. Кода не меняем. При приёмке — проверить ответ в треде на реальном PR; если не встаёт в тред —
отдельная задача.

## Не делаем

- Пункт 5 (рефакторинг `register.ts`) — отдельная спека в конце.
- Issue в Forgejo для роадмапа.
- Автоматическое исправление неблокирующих — только TODO и роадмап.

## Что проверить

- Агент ставит `blocking` только с категорией; без неё находка отбрасывается.
- Вердикт: только неблокирующие → одобрение с комментариями; одна блокирующая → запрос изменений.
- Свой PR: неблокирующее замечание → TODO в коде + пункт роадмапа + ответ «Перенесено в TODO»; повторный раунд не
  дублирует пункт.
- Без `policy.ts` мод регистрируется, прогоны работают; `manualCommitCommands` в старом конфиге не ломает загрузку.
- Следующий `/pr` молча убирает брошенные папки прогонов, старые гайды и законченные вкладки, не трогает живые прогоны.
- CI падает при непрошедшем тесте и при неподнятой версии.

## Порядок работы

Каждая часть — свой PR и своя версия: 1 (блокирующие) → 2 (без запретов) → 3+4 (уборка и пагинация) → 5 (CI).
План реализации пишется перед каждой частью.
