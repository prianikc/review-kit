# Спека: конфликты в `/pr` и скилл `/confl`

## Контекст

Сейчас `/pr` не показывает, что PR конфликтует с базой: это видно только на сайте или при попытке влить. Разрешать
конфликты приходится вручную, а внутри прогона guard ещё и запрещает `pull`/`rebase`. Нужно:

1. в списке `/pr` видеть конфликт у каждого PR, а свой PR с конфликтом получать как «дело»;
2. скилл `/confl`, который разрешает конфликты. Его вызывают человек (`/confl`), главный цикл и другие скиллы.

## Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Режимы `/confl` | без аргумента — конфликты, уже лежащие в дереве; `/confl N` — свой PR N: влить базу и разрешить | выбор пользователя |
| Как подтягивать базу | `git merge origin/<база>` в ветку PR, обычный push | без `--force` и переписывания истории; guard остаётся как есть |
| Влияние на `/pr` | метка «конфликт» у любого PR; свой PR с конфликтом — дело со своим сценарием | выбор пользователя |
| Имя | скилл `confl`, команды мода `/confl` нет | инвариант: имя команды мода ≠ имя скилла |

## Признак конфликта (хостинг)

- `PullRequest` получает поле `conflicted: boolean`.
- Адаптер Forgejo/Gitea: `conflicted = state === 'open' && !merged && mergeable === false` (поле `mergeable` есть
  в ответе списка и одного PR). Пока сервер пересчитывает слияние, `mergeable` бывает `false` — короткая ложная метка
  допустима: `/confl N` всё равно проверяет конфликт настоящим merge.
- Фейковый провайдер получает то же поле. Ядро про `mergeable` не знает.

## Список `/pr`

- Строка PR: `#N <статус> · конфликт · <автор> — <заголовок>` — метка только при `conflicted`.
- Новый сценарий `conflict`: свой открытый PR с конфликтом и без новых замечаний. Если есть замечания — сценарий
  `feedback` (замечания важнее; метка в строке всё равно видна). Статус сценария — «конфликт».
- `conflict` входит в `ACTIONABLE`: PR попадает в «PR, по которым есть дело» и в меню.
- Выбор такого PR (`/pr N`, меню, `review_start`) передаёт управление скиллу: «Use the review-kit:confl skill for PR N».
- `/pr all`: свой PR размещается так же, как свои PR сейчас (на ветке текущего дерева — здесь, иначе во вкладке),
  вкладка получает `/confl N`.

## `/confl N` — свой PR

Поток:

1. Скилл вызывает новый инструмент мода `conflict_start {pr}`. Мод:
   - проверяет, что PR свой и открыт (иначе отказ с текстом);
   - спрашивает про активный прогон так же, как при старте других сценариев;
   - переключает дерево на ветку PR существующими `planSwitch`/`applySwitch` и открывает прогон со сценарием
     `conflict` (guard включён);
   - выполняет `git merge --no-ff --no-commit origin/<база>`;
   - нет конфликтов → `git merge --abort`, закрывает прогон, отвечает «Конфликтов с базой нет» (база не вливается);
   - есть конфликты → отвечает списком файлов с конфликтом.
2. Скилл разрешает каждый файл по смыслу обеих сторон (читает `git diff`, историю обеих веток), убирает маркеры,
   `git add <файл>`. Не может уверенно решить файл → спрашивает человека (`AskUserQuestion`) с вариантами.
3. Скилл вызывает `commit_push {pr, message, paths}`, `paths` — файлы с конфликтом. В прогоне `conflict` мод:
   - проверяет, что неразрешённых путей нет и в `paths` нет маркеров `<<<<<<<`/`>>>>>>>`;
   - коммитит слияние (в индексе — весь merge, не только `paths`; это допустимо только при `MERGE_HEAD`);
   - сам спрашивает подтверждение и пушит обычным push.
   Раунд для слияния: первый родитель коммита — база раунда.
4. `review_finish`.

Отказ человека в подтверждении → слияние остаётся закоммиченным локально, прогон закрывается, отчёт говорит, как
допушить (`/confl N` снова — мод увидит непушенный коммит слияния и предложит push).

## `/confl` без аргумента — текущее дерево

Только скилл, без мода:

1. По `git status` определить операцию: merge, rebase, cherry-pick, revert, или конфликт после `stash pop`/`apply`.
   Конфликтов нет → «Конфликтов нет», стоп.
2. Разрешить каждый файл (как в шаге 2 выше), `git add`.
3. Продолжить операцию: merge → `git commit --no-edit`; rebase/cherry-pick/revert → `git <op> --continue`
   (`GIT_EDITOR=true`); новые конфликты следующего коммита rebase — повторить. Stash — не продолжать и не удалять:
   сказать, что stash сохранён.
4. Внутри активного прогона review-kit guard отклонит продолжение — тогда остановиться после `git add` и сообщить, что
   файлы разрешены и проиндексированы; продолжает вызвавший скилл или человек.
5. Никогда: push, `--abort` без просьбы, `--force`, `reset --hard`, `checkout --theirs/--ours` целого файла без
   проверки смысла.

## Скилл `confl`

- `skills/confl/SKILL.md`, без `disable-model-invocation` — вызывается человеком, моделью и из других скиллов.
- `argument-hint: "[номер PR]"`. Описание — когда срабатывает: конфликты merge/rebase в дереве, PR с конфликтом.
- Текст скилла на английском, всё видимое пользователю — на русском.

## Ошибки

| Ситуация | Ответ |
|---|---|
| `/confl N`, PR чужой или закрыт | отказ: «PR N не ваш / закрыт — конфликты разрешает автор» |
| Дерево грязное перед переключением | существующий отказ `applySwitch` («сначала stash») |
| Ветка PR занята другим worktree | существующий отказ `planSwitch` |
| Push отклонён (ветку обновили) | как в раунде правок: «подтяните ветку и повторите `/confl N`» |
| pre-commit упал | вывод хука, коммита нет, прогон открыт до `review_finish` |
| В дереве уже идёт другая операция при `/confl N` | отказ: «в дереве идёт merge/rebase — `/confl` без номера» |

## Вне объёма

- rebase и `--force-with-lease`;
- разрешение конфликтов в чужих PR;
- автоматический вызов `/confl` из `pr-fix-run` при отказе push (только подсказка в тексте отказа);
- адаптеры других систем.

## Тестирование

- адаптер: `mergeable: false` → `conflicted: true`; `mergeable: true`, закрытый, влитый → `false`;
- `scenarioOf`: свой + конфликт → `conflict`; свой + конфликт + замечания → `feedback`; чужой + конфликт — прежний
  сценарий; `statusOf` → «конфликт»;
- строка списка с меткой и без;
- git (временные репозитории `mod/testing/`): merge с конфликтом → список файлов; чистый merge → abort и дерево
  как было; коммит слияния с проверкой маркеров и неразрешённых путей; раунд слияния — первый родитель;
- policy: в прогоне `conflict` по-прежнему отклоняются сырые `commit`/`push`.
