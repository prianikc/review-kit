# review-kit

**Универсальный** плагин Claude Code для работы с pull request'ами: ревью чужих PR воронкой агентов, разбор замечаний к своему PR,
раунд правок, перепроверка после своего ревью. Всё в текущей вкладке; параллельные ревью во вкладках Orca через `pr-tab`.

Плагин не привязан к одному хостингу. При установке пользователь выбирает, с какими системами работает; каждая система —
отдельный адаптер. В 3.0 есть только адаптер **Forgejo/Gitea** (для него известны команды и API), GitHub, GitLab и другие
добавляются позже, без изменений ядра. Код 2.2.0 пока написан только под Forgejo — это и переделывается.

## Текущее состояние: идёт переделка 2.2.0 → 3.0

`PLAN.md` — утверждённый план переделки, главный документ для текущей работы. Перед изменениями сверяйся с ним:
что удаляется целиком (lite, simplify, проверки, стек и правила, Plannotator, установщик, миграция 1.17), что переезжает в мод,
как устроены адаптеры хостингов и выбор системы при установке, и в каком порядке всё делается. Код в репозитории пока версии 2.2.0 — многое из описанного ниже ещё существует, но обречено.

Версия — только в `.claude-plugin/plugin.json`.

## Устройство

| Путь | Что это |
|---|---|
| `.claude-plugin/` | `plugin.json` (манифест) и `marketplace.json` (локальный маркетплейс с одним плагином) |
| `hooks/hooks.json` | подключает мод: `{"modules": ["../mod/register.ts"]}` |
| `mod/register.ts` | мод (TS, API из `'claude-code'`): команды `/pr`, `/pr-review`, `/pr-feedback`, `/pr-fix`, `/pr-recheck`; инструменты `review_start`, `review_confirm`, `review_finish`, `review_plannotator`; хуки и состояние прогона |
| `mod/policy.ts` | разбор bash-команд: во время прогона запрещает сырые `git push`/`commit`, `curl` на запись, `--force`, `--amend` |
| `mod/gate.ts` | gate чтения: агент не может вернуть ответ, пока не прочитал целиком файлы своего манифеста |
| `types/index.d.ts` | типы состояния плагина (`PluginState['review-kit']`) |
| `funnel/review-funnel.js` | Workflow-скрипт: агенты A/B ищут находки → C опровергает |
| `funnel/triage.js` | Workflow-скрипт: агент D классифицирует замечания (feedback / recheck) |
| `agents/` | `correctness` (A), `quality` (B), `refuter` (C), `triage` (D); без Edit/Write, запускаются только из workflow |
| `skills/` | `pr-flow` (вход по словам), `pr-review-run`, `pr-feedback-run`, `pr-fix-run`, `pr-recheck-run`, `pr-tab` |
| `tools/` | Python/bash-скрипты (Forgejo API, подготовка входа агентам, payload, commit-push, cleanup). По плану весь `tools/` переезжает в мод (`forge/`, `status.ts`, `run.ts`, `git.ts`) и исчезает |
| `config/` | пороги воронки (`funnel.json`), пример настроек проекта |

Целевая структура мода 3.0 (из `PLAN.md`): `mod/forge/types.ts` (интерфейс `ForgeProvider` и общая модель PR / ревью /
комментарий / тред / вердикт), `mod/forge/index.ts` (реестр адаптеров и выбор по `git remote`), `mod/forge/forgejo.ts`
(первый адаптер), `mod/status.ts` (сценарий и статус PR без обращений к API), `mod/run.ts`, `mod/git.ts`.

Рабочие файлы прогона в целевом проекте: `.review-kit/run/<N>/` (`context.json`, `intake.json`, вход и ответы агентов).

## Инварианты (не ломать при изменениях)

- **Имя команды мода и имя скилла никогда не совпадают** (`/pr-feedback` — команда, `pr-feedback-run` — скилл). Конфликт
  регистрации роняет `session.start`, и в сессии не остаётся ни одного инструмента review-kit.
- Необратимые действия (публикация ревью или ответов, commit+push раунда) — только после инструмента `review_confirm`.
  «Да» в чате не считается: мод ставит метку ровно на подтверждённые аргументы.
- Внутри активного прогона внешние эффекты идут только через инструменты/скрипты кита; мод отклоняет сырые команды.
- Каждая остановка скилла заканчивается `review_finish` — открытый прогон держит guard включённым.
- Ветки и stash удаляются только через вопросы мода (`/pr cleanup`), не по инициативе агента.
- Находка агента обязана нести сценарий отказа; без него отбрасывается.
- Агенты A–D запускаются только своими типами (`review-kit:correctness` и т.д.) через workflow, не `general-purpose`/`Explore`:
  только на них висит gate.

## Принципы 3.0 (кратко, подробно — в `PLAN.md`)

- **Ядро не знает о хостинге.** Сценарии, статусы, воронка, скиллы и агенты работают с общей моделью. Всё, что зависит от
  системы (URL API, токен, формат ответов, маппинг вердиктов на `APPROVED`/`REQUEST_CHANGES`/комментарий), — только в её
  адаптере в `mod/forge/`. Вне адаптера не писать «Forgejo», `/api/v1` и т.п.; в текстах для пользователя — просто «PR».
- Новая система = новый файл в `mod/forge/` + регистрация + юнит-тесты маппинга. Если для этого приходится менять ядро,
  скилл или агента — значит, интерфейс протёк, чинить интерфейс.
- Чего система не умеет (inline-комментарии, resolve тредов, request changes), адаптер сообщает через `capabilities`,
  а ядро деградирует явно, а не гадает.

- Ноль внешних зависимостей: плагин не читает и не требует `CLAUDE.md`, `AGENTS.md`, `.claude/rules`, nx, Python, Plannotator,
  superpowers. Единственное исключение — Orca для `pr-tab`, с fallback на текущее дерево.
- Ничего не копируется ни из плагина в проект, ни обратно.
- Детерминированная работа — в моде; в скилле только то, что требует суждения модели. Скиллы короткие, без «run python3 …».
- Минимум кода: каждый файл проходит проверку «нужен ли он вообще».

## Соглашения

- Всё, что видит пользователь (тексты команд, вопросы, отчёты, сообщения мода), — на русском.
  Тексты скиллов и промпты агентов — на английском.
- Стиль TS в `mod/`: без точек с запятой, одинарные кавычки, константы `UPPER_CASE` в начале файла.
- Формат отчёта ревью и вердикты — в `skills/pr-review-run/SKILL.md`, раздел 2. Маппинг вердиктов на состояния
  хостинга по плану переезжает в адаптер.

## Запуск и проверка

- Сборки и тестов пока нет (нет `package.json`/`tsconfig`); юнит-тесты мода появятся при переносе `tools/` в TS.
- Локальный запуск: из корня тестового проекта `claude --plugin-dir /home/prian/projects/review-kit`. Скиллы ссылаются
  на скрипты через `${CLAUDE_PLUGIN_ROOT}`, установка в проект не нужна.
  Проверять нужно на репозитории с remote на поддерживаемой системе (в 3.0 — Forgejo/Gitea); токен — переменная окружения
  адаптера (`FORGEJO_TOKEN`).
- Ядро тестируется на фейковом провайдере: сценарии `review`, `recheck`, `feedback`, `wait-author` должны проходить без
  настоящего хостинга.
- Глобально у пользователя включены superpowers, agent-skills (`/review`, агент `code-reviewer`) и plannotator — при ручной
  проверке они могут перехватить запросы «посмотри PR». Проверять через явные `/pr…` команды.
- Финальная проверка чистоты из `PLAN.md`:
  `grep -rE "python3|ai-dev-kit|nx |apps/|best-practices|CLAUDE\.md|AGENTS\.md|\.claude/rules|plannotator|simplify|review-lite|1\.17|\.claude/skills/review-kit"`
  по плагину не должен ничего находить (кроме `PLAN.md` и этого файла).
