# review-kit

**Универсальный** плагин Claude Code для работы с pull request'ами: ревью чужих PR воронкой агентов, разбор замечаний к своему PR,
раунд правок, перепроверка после своего ревью. Всё в текущей вкладке; параллельные ревью во вкладках Orca через `pr-tab`.

Плагин не привязан к одному хостингу. При установке пользователь выбирает, с какими системами работает; каждая система —
отдельный адаптер. В 3.0 есть только адаптер **Forgejo/Gitea** (для него известны команды и API), GitHub, GitLab и другие
добавляются позже, без изменений ядра.

## Состояние

Версия 3.0. Спека — `docs/superpowers/specs/2026-10-12-review-kit-3-design.md`; `PLAN.md` — исходный план, решения спеки
его уточняют. Платформа — POSIX (Linux, macOS, WSL), git ≥ 2.31, Node 24.

## Устройство

| Путь | Что это |
|---|---|
| `.claude-plugin/` | `plugin.json` (манифест, версия, `userConfig` — галочка системы) и `marketplace.json` |
| `hooks/hooks.json` | подключает мод: `{"modules": ["../mod/register.ts"]}` |
| `mod/register.ts` | команды `/pr`, `/pr-review`, `/pr-feedback`, `/pr-fix`, `/pr-recheck`; инструменты `review_start`, `review_prepare`, `review_collect`, `review_publish`, `replies_publish`, `commit_push`, `review_plannotator`, `review_tab`, `review_finish`; хуки и состояние прогона |
| `mod/forge/` | общая модель хостинга (`types.ts`), выбор адаптера и токена (`index.ts`), адаптер Forgejo/Gitea (`forgejo.ts`), фейковый провайдер для тестов |
| `mod/status.ts` | сценарий и статус PR, intake замечаний, прошлые замечания для перепроверки |
| `mod/run/` | вход агентам и поиск правил (`input.ts`), сбор находок и триажа (`findings.ts`), тело ревью и ответы (`review.ts`) |
| `mod/git.ts` | переключение на PR, снимок раунда, commit+push, уборка, worktree для `pr-tab` |
| `mod/plannotator.ts` | аннотации находок и разбор решения Plannotator |
| `mod/policy.ts` | во время прогона запрещает сырые `git commit`/`push`/`pull`/`rebase`, `--force`, `--amend`, curl/wget-запись |
| `mod/gate.ts` | gate чтения: агент не вернёт ответ, пока не прочитал целиком файлы своего манифеста |
| `mod/testing/` | временные git-репозитории для тестов |
| `types/index.d.ts` | типы состояния плагина |
| `funnel/` | Workflow-скрипты: `review-funnel.js` (A/B → C), `triage.js` (D) |
| `agents/` | `correctness` (A), `quality` (B), `refuter` (C), `triage` (D); без Edit/Write, запускаются только из workflow |
| `skills/` | `pr-flow`, `pr-review-run`, `pr-feedback-run`, `pr-fix-run`, `pr-recheck-run`, `pr-tab` |
| `config/funnel.json` | пороги воронки |

Рабочие файлы прогона в целевом проекте: `.review-kit/run/<N>/` (`context.json`, `intake.json`, вход и ответы агентов).

## Инварианты (не ломать при изменениях)

- **Имя команды мода и имя скилла никогда не совпадают** (`/pr-feedback` — команда, `pr-feedback-run` — скилл). Конфликт
  регистрации роняет `session.start`, и в сессии не остаётся ни одного инструмента review-kit.
- Необратимые действия (публикация ревью или ответов, commit+push раунда) — только инструментами `review_publish`,
  `replies_publish`, `commit_push`: каждый сам спрашивает подтверждение, «да» в чате не считается.
- Внутри активного прогона внешние эффекты идут только через инструменты мода; мод отклоняет сырые команды.
- Каждая остановка скилла заканчивается `review_finish` (кроме остановок Plannotator в `pr-fix-run`) — открытый прогон держит guard включённым.
- Ветки и stash удаляются только через вопросы мода (`/pr cleanup`), не по инициативе агента.
- Находка агента обязана нести сценарий отказа; без него отбрасывается.
- Агенты A–D запускаются только своими типами (`review-kit:correctness` и т.д.) через workflow, не `general-purpose`/`Explore`:
  только на них висит gate.

## Принципы 3.0 (кратко, подробно — в `PLAN.md`)

- **Ядро не знает о хостинге.** Сценарии, статусы, воронка, скиллы и агенты работают с общей моделью. Всё, что зависит от
  системы (URL API, токен, формат ответов, маппинг вердиктов на `APPROVED`/`REQUEST_CHANGES`/комментарий), — только в её
  адаптере в `mod/forge/`. Вне адаптера не писать «Forgejo», `/api/v1` и т.п.; в текстах для пользователя — просто «PR».
- Новая система = новый файл в `mod/forge/` + регистрация + юнит-тесты маппинга. Если для этого приходится менять ядро,
  скилл или агента — значит, интерфейс протёк, чинить интерфейс.
- Чего система не умеет (inline-комментарии, resolve тредов, request changes), адаптер сообщает через `capabilities`,
  а ядро деградирует явно, а не гадает.

- Плагин не требует правил проекта, Python и nx. Агент B использует правила, если они есть в репозитории (у чужого PR —
  с базы). Внешние зависимости: Plannotator и superpowers — раунд правок; Orca — `pr-tab` (без неё ревью в текущем дереве).
- Исключение из «ядро не знает о хостинге»: валидатор требует литеральные имена в `$.env.get`, поэтому переменные
  токена (`FORGEJO_TOKEN`, `GITEA_TOKEN`) читаются в `register.ts` (`readTokens`); новая система добавляет туда строку.
- Ничего не копируется ни из плагина в проект, ни обратно.
- Детерминированная работа — в моде; в скилле только то, что требует суждения модели. Скиллы короткие, без «run python3 …».
- Минимум кода: каждый файл проходит проверку «нужен ли он вообще».

## Соглашения

- Всё, что видит пользователь (тексты команд, вопросы, отчёты, сообщения мода), — на русском.
  Тексты скиллов и промпты агентов — на английском.
- Стиль TS в `mod/`: без точек с запятой, одинарные кавычки, константы `UPPER_CASE` в начале файла.
- Формат отчёта ревью и вердикты — в `skills/pr-review-run/SKILL.md`, раздел 2; маппинг вердиктов на состояния хостинга — в адаптере.

## Запуск и проверка

- Тесты: `node --test 'mod/**/*.test.ts'` (без зависимостей; компилятора TypeScript нет — код в «стираемом» TS).
  Проверка плагина: `claude plugin validate .`.
- Локальный запуск: из корня тестового проекта `claude --plugin-dir /home/prian/projects/review-kit`. Скиллы ссылаются
  на файлы плагина через `${CLAUDE_PLUGIN_ROOT}`. Токен — `FORGEJO_TOKEN` (или `GITEA_TOKEN`) в окружении.
- Глобально у пользователя включены superpowers, agent-skills и plannotator — при ручной проверке они могут перехватить
  запросы «посмотри PR». Проверять через явные `/pr…` команды.
